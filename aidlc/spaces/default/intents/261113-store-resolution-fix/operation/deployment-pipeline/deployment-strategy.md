# 配りの方式（取り組み 261113-store-resolution-fix）

この文書は、配りの方式の選び（選んだ物と選ばなかった物）、束を進める門、新旧が同居する間の安全、止める条件を書く。手順と道具は `cd-config.md`、戻しは `rollback-runbook.md`。決まっている物の出どころは、Owner の決定 `OD-KUSABI-STORE-RESOLUTION-RELEASE-PRODCHECK-R1-SELF-SEATS-20261116-001`（https://github.com/watchout/iyasaka-arc/issues/49#issuecomment-6910764201 ）と `team.md` の Deployment。

## 1. 方式（選んだ物と、選ばなかった物）

選んだ方式は、**席の束ごとの段階の配り**（canary に近い。束は R1 → R2 → R3 の順で、各束は、その束のすべての席が健全と観測されてから次へ進み、失敗した束は設定を元に戻す = `team.md`）。今回の許可は R1（Kusabi 自身の 2 席）だけ。

| 方式 | 判断 | 理由 |
|---|---|---|
| 席の束ごとの段階の配り | **選ぶ** | `team.md` の決まりで、Owner の決定の 3 もこの形。失敗の広がりが 2 席に収まる |
| 全席に一度に配る | 選ばない | Owner の許可が Kusabi 自身の 2 席だけ（決定の 3）。ほかの席は R1 の観測の後に改めて伺う |
| blue/green | 使わない | 切り替える通信が無く、席が自分の hook の設定を読むだけ。ただし、差し替える前の版は置き場に消されず残るので、戻し先が残る性質だけは同じ（`rollback-runbook.md`） |
| rolling（同じ束の中を順に） | 使わない | 今回の束は 2 席で、1 席ずつの順は Owner が打つ script の中の話（読んでいない） |
| main からの自動の配り（continuous deployment） | 選ばない | 配りは保護面（版の置き場・席の hook）で、Owner が打つ。workflows を足すにも Owner の exact-head が要る |

## 2. R1 から R2 に進む門（Q1 = B）

答え（arc の答え。Owner の決定 95）: 各席で、hook を差し替えた後の最初の Stop の証拠が、決めた保存先と一致し `store_refused` が 0 件であることに加えて、各席で 1 回、Stop が保存した引き継ぎを、同じ保存先から `restart-cli` で読み戻せること。2 席とも満たす。

結果は 3 値（一致・不一致・観測できず）。**観測できずを成功に数えない**（S5）。観測の値は、開いた store の観測から取り、宣言を写さない。

| 観測 | 見る物 | 「一致」と数える条件 | 「観測できず」になる時 |
|---|---|---|---|
| 1（各席） | 差し替えの後の最初の Stop の証拠（`session-rotation-stop`・`transcript-stop-capture` が出す JSON） | `store_backend` と `store_source` が入り（null でない）、席ごとの期待と一致し、`reason` が `store_refused:` で始まらない | その席で Stop がまだ起きていない・証拠を取り出せない。**Claude の席の回転の Stop は、まだ起きていない**（arc の答え） |
| 2（各席 1 回） | Stop が保存した引き継ぎを `restart-cli` で読み戻す | 読み戻した先が、観測 1 で証拠が示した保存先と同じ | 読み戻しを行う許可・結果が無い |

この門には、2 つの未決の点がある。どちらも、Deployment Execution の始めに、席が Owner と arc に確かめる（この段では決めない）。

- **席ごとの期待（`store_backend`・`store_source` の値）**: この記録には無い。URL・path は証拠に出ないので、席が設定 file の中身を読んで作るのでなく（Q2 = B は hash だけ）、差し替えの前に Owner か arc が各席の期待を出し、記録に先に書く。期待が出なければ、「一致」と判定できず「観測できず」とする。
- **観測 2 の読み戻しは、本番の保存先を読む**。Q2 = B の席は DB を読まないので、読み戻しは Owner か arc の script の出力を、席がデータとして読む形になる。本番の DB を読む許可は、今の決定（表と列の名前だけ）に入っていない。読み戻しの許可と script を、誰がどの形で出すかは、Owner の判断に回す。

差し替えの確かめ（Q2 = B）: 差し替えの前と後の 2 席の設定 file の hash を、席が**読むだけ**で比べ、script の出力と食い違わないかを見る。書かない・直さない。前の版の hash は、install4 の log と #49 6911141083 の記録にある（arc の答え）。席の設定 file の中身（hook の command など）は記録に写さない。hash と、差し替えた hook の数・版の識別子だけを書く。

## 3. 新旧の同居（S6）

- DB の構造は変えないので migration は無い。証拠の項目は足すだけで（`store_backend`・`store_source` の 2 つ。既存の項目と schema の const は変えない）、旧い読み手は壊れない（`requirements.md` の FR4.4・NFR7）。
- 差し替えは席ごとに行うので、2 席のうち 1 席だけが新しい版になる時がありうる。版は追加だけで上書きしないので、1 席が古い版を指したままでも、置き場にある版の中身は変わらない（置き場の性質。2 席が同時に別の版で動く間の振る舞いは、試験していない）。
- 新しい Stop は、これまで黙って既定の SQLite に落としていた入力（未知の `AGENT_MEMORY_DB_TYPE`・postgres の形でない `DATABASE_URL`）を拒否する（`requirements.md` の AS5・OQ2）。拒否の回は、host を止めず（出力は「続ける」のまま）、証拠に `store_refused:<理由>` を残し、SQLite の file を作らない（`build-and-test-summary.md` の BT-14）。つまり、席が止まるのでなく、保存されないことが「拒否」として見える。R1 の観測 1 が見るのは、この拒否の 0 件。
- 既存の版は消さない。差し替えは設定の書き換えで、版の置き場には触れない。

## 4. 止める条件

次のどれかで、束を進めるのを止める（`KUSABI_ALPHA_FLEET_ROLLOUT.md` の 8 のうち、今回の配りに当たる物と、Owner の決定の 3）。

- 2 席のうち 1 席でも、観測が「不一致」になる（その席の差し替えだけを戻して止まる。決定の 3）。
- 席の設定 file の hash が、script の出力と食い違う（期待した版・設定の hash が違う）。
- 公開した版の識別子・統合の commit が、承認された物と違う（`--expected-head` の不一致を含む）。
- 戻しの材料（差し替える前の設定の backup）が無い。
- 自動の再起動・端末への入力・信頼の設定の変更・関係のない作業場の変更が起きた。
- 独立の監査が、止める指摘を出した。
- 「観測できず」が続く: 成功に数えず、進めない（待ち: Owner の判断か、Stop が起きること）。

止めた後に再開するには、戻しの確認と、新しい Owner の決定が要る（`KUSABI_ALPHA_FLEET_ROLLOUT.md` の 9 の最後）。

## 5. 確かめたことと、確かめていないこと

- 確かめた: 方式の選び（`team.md`・Owner の決定・`KUSABI_ALPHA_FLEET_ROLLOUT.md` を読んだ）、拒否の回の振る舞い（`build-and-test-summary.md` の BT-14。試験で確かめた物）。
- 確かめていない: 席が実際に差し替わったか、2 席の観測 1・2 の結果（どれも観測できていない）。席ごとの期待も、まだ無い。
