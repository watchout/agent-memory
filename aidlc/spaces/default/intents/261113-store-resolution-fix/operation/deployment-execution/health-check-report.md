# 配った後の健全性の報告（取り組み 261113-store-resolution-fix）

この報告は、R1（Kusabi 自身の 2 席）へ版 `eb9bf298…` を配った後の様子を、席ごとに読む。確かめの 1 行ずつは `smoke-test-results.md`（S-01〜S-17）、経過と hash は `deployment-log.md`。席は読むだけで、版の置き場・本番の DB・tmux に触れていない。結果は 3 値（一致・不一致・観測できず）で、観測できずを健全に数えない（S5）。Operation 段階の決まり（新しい service には health の指標と誤り率の指標を 1 つずつ）は、この取り組みには当てはまらない: 新しい service は無く、既存の hook の保存先の決め方を直した取り組みで、運用の指標は足していない（足すなら、新しい取り組み）。

## 1. R1 の判定（前の段の Q1 = B の定義に対して）

| 席 | 観測 1: 差し替えの後の最初の Stop の証拠が期待と一致、`store_refused` が 0 件 | 観測 2: Stop が保存した引き継ぎを `restart-cli` で同じ保存先から読み戻せる | 席の判定 |
|---|---|---|---|
| A（Claude の席） | 観測できず（Q3 の答え = B） | 観測できず（Owner が打つ script の出力待ち） | **観測できず** |
| B（Codex の席） | 観測できず（席が動いていない。同上） | 観測できず（同上） | **観測できず** |

**R1 の判定: 観測できず。** 2 席とも満たしていない。前の段の決め（観測できない間は成功に数えない）により、R2 以後に進める判断を Owner に伺う材料は無い。

観測 1 は、Q3 の答え（B）により、この取り組みでは「観測できず」のままになる（Stop の証拠は stderr に出るだけで残らない）。観測 2 が出て「一致」になっても、観測 1 は満たされない。その状態で R2 に進むかは、Owner の判断（席は決めない）。

## 3. 期待の保存先と、いまの席の状態

- 期待（arc の記録 https://github.com/watchout/iyasaka-arc/issues/49#issuecomment-6943475955 、SHA-256 `5a42d79d70de5846aa71eaba82a760af85256b20009e39cd6302197b53abc6bd`）: A・B とも backend = postgres、source = user_config。決め方は要件の FR1.2 の順（環境変数の種類が無く、環境変数の URL が無く、設定 file に `database_url` がある）。
- その根拠は「席の起動の道に 3 つの変数の設定が 0 件」という arc の読み（名前と真偽だけ）。**動いている process の環境そのものは、arc も席も読んでいない**（値が出るので）。期待は、起動の道からの推論で、動いている process の観測ではない。
- 設定 file にだけ接続先がある席は、これまで Stop が既定の SQLite を黙って開いていた（直す不具合）。直った版では、postgres に決まる。直す前の版が動いていた席は、新しい版に切り替わるまで SQLite を開く。A は起動が差し替えの後なので新しい版のはずだが、run 記録に版が出ないので、確かめていない。

## 4. 保存の欠けの可能性（2026-11-17 10:49〜15:23 JST）

- 事実（arc の記録 https://github.com/watchout/iyasaka-arc/issues/49#issuecomment-6940564525 、SHA-256 `30559ee313605486bcbe00dfb1f7385eabfbeab44176e3828a842ad6358cb7ee`）: 10:49〜15:23 JST の間、PostgreSQL が loopback の TCP の接続を拒んでいた。Owner が 15:24 JST に戻し、その後の拒否は 0（arc が 15:24:45 JST に数えた）。arc は、Kusabi の保存先の設定も agent_comms を TCP の loopback で指していると書く（道の種類と DB 名だけを読んだ）。
- code を読んだ事実（版 `fa9f3a2f…` の `src/transcript-stop-capture.ts`）: Stop ごとの取り込みは、会話の記録の**末尾 4 MiB** だけを読み（`snapshot_mode: "tail"`、`TRANSCRIPT_CAPTURE_TAIL_BYTES = 4 * 1024 * 1024`）、取り込みが例外になれば `ingest_failed` の証拠を出して「続ける」を返す。取り込みには重複の数（`events_duplicate`）があり、同じ事象を二重に数えない作りだが、**どこまで保存したかの印（cursor）は読んだ範囲に無い**。
- つまり、その窓の間に Stop の保存が失敗した場合、次の Stop が 4 MiB の末尾に収まる分は補われる可能性があるが、収まらない分は欠ける可能性がある。この席の会話の記録は、2026-11-18T21:09Z の時点で 211,967,807 bytes（約 202 MiB）あり、末尾 4 MiB はその約 2% にすぎない。窓の間（約 4.5 時間）に増えた量が 4 MiB を超えたかは、記録の時刻を数えていないので確かめていない。収まらなければ、窓の先頭の分は後の Stop でも取り込まれない。
- 席が確かめられるか: **確かめられない**（DB を読まない範囲）。Q4 の script が、その窓の保存の欠けを件数だけで見られるかを、arc に確かめる（行の値は出さない）。結果は、観測できず。
- この欠けは、直す前から続く保存の失敗（設定 file にだけ接続先がある席で、Stop が壊れた SQLite を開く不具合）とは別の物。差し替えの前の版が動いていた間は、そもそも TCP の postgres を開いていなかった可能性がある。どちらの版で何が起きたかは、記録に版が出ないので、席は区別できない。

## 5. 席の再起動と切り直しについて

- 差し替えは設定 file の書き換えだけで、動いている process の hook は書き換えない。A の process は差し替えの後の起動なので新しい設定を読む起こり方だったが、読み込みの確かめは無い。B は動いていないので、次に起動した時に新しい設定を読む。
- 自動で再起動しない・端末に入力しない・信頼の設定を変えない（`KUSABI_ALPHA_FLEET_ROLLOUT.md` の 9）。席の起こし直しは、人が普通に閉じて起こす。
