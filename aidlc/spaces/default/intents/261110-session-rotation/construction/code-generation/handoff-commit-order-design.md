## 4. 採る案（A）の設計（4 回目の版から: 出力 → 出力済みの記録 → 消費。5 回目の版は見張りの終端の値を足した）

### 4.1 読む側（`prepareRotationRecovery`）
1. **読むだけ**にする。`getSelectedRestartPack`、`sha256` の突き合わせ、`redactText`、文の組み立てまでを行い、`consumeSelectedRestartPack` は呼ばない。`turn` file の `started` は今と同じく書く（見張りへの射影。引き継ぎの無い起動でも書かれる）が、`rotation_marker_id` は claim 経由でも**常に null** で書く（確認は 4.6 の出力済みの記録に移す）。
2. 戻り値の `RotationBlock` に、確定の計画 `commit` を足す。中身は**データだけ**（関数・store を持たない）: `query`（`agent_id`・`project`・`pack_ref`）、`directory`（席の置き場）、`turn`（今書いた `turn` の中身。出力済みの記録の元になる。`rotation_marker_id` は null、`at` と身元を含む。`started` の書き込みが失敗した時は null）、`marker_id`、`via`（`"claim"` か `"marker"`）。`text`・`initial_user_message`・`marker_id` は今のまま。

### 4.2 確定の計画が process 層に届く道（内部の型の変更だけ。出力・証拠の形は変えない）
- `RotationBlock.commit` → `LoadedCodexRecovery.rotation`（Claude と Codex の loader は既に `rotation` を返す。`claude-session-start.ts:383`・`codex-session-start.ts:878`）→ `runCodexSessionStart` が `rotation_evidence` を付ける所（`codex-session-start.ts:940`）で `rotation_commit` も付ける → `runClaudeSessionStart` が `rotation_evidence` を写す所（`claude-session-start.ts:472`）で同じく写す。`runClaudeSessionStart` は `runCodexSessionStart` を包むので、結果の型を 2 か所（`CodexSessionStartRunResult` の `rotation_evidence` の行 `codex-session-start.ts:248`／`ClaudeSessionStartRunResult` の同じ行 `claude-session-start.ts:168`）に足す。
- process 層が書くのは `result.output`（stdout）と `result.evidence`（stderr）だけ（`claude-session-start.ts:537-547`・`codex-session-start.ts:1031-1036`）。`rotation_commit` は書かない。出力の bytes は変わらない（T4 で固定）。
- **確定の対象かどうかは `rotation_commit` があるかで決める**（= 引き継ぎの文が出力の `additionalContext` に入ったか）。結果の `outcome`（full／degraded）では決めない。理由: 品質ログの書き込みが失敗すると `outcome` は degraded（`EVIDENCE_LOG_UNAVAILABLE`）になり `systemMessage` が付くが、`additionalContext` には引き継ぎの文が入る（`codex-session-start.ts:911`・`922-935`）。この場合は文が出力に入るので確定する（T10）。回復の読み込みが例外・期限で終わった時は `loaded` が返らないので `rotation_commit` も付かず、確定しない（F1・F2）。
- 証拠（`wasurezu-session-rotation-start/v1`）は `marker_id`・`token_estimate`・`byte_count`・`truncated`・上限だけで、『消費した』『記録を書いた』とは言わない（`session-rotation-start.ts:70-78`）。確定を後ろへ移しても、証拠が事実より先に宣言することは無い。

### 4.3 確定（`commitRotationRecovery`。名前は下書き）と、その順

引数: 確定の計画、store を開く関数、`now`（S4）、`elapsed_ms()`（process の開始からの経過。呼ぶ側の単調時計）、`hook_timeout_ms`（呼ぶ側の hook の期限）。呼ぶのは出力（stdout）の書き込みが成功した後だけ（4.4）。次の順で進み、**戻せない一歩（消費）は、事実を残す手（出力済みの記録）が済んだ後にだけ行う**。

| 段 | 何をするか | 失敗・遅れた時 |
|---|---|---|
| 0 | `commit_by = hook_timeout_ms − ROTATION_COMMIT_EXIT_MARGIN_MS`（9 秒 − 2 秒 = process の開始から 7 秒）。残り = `commit_by − elapsed_ms()`。残りが `ROTATION_COMMIT_WRITE_RESERVE_MS` 未満なら、何もせず終わる（記録も消費も無い。束は `active` のまま） | 席の出力は出ている。→ 4.7 の P1 |
| 1 | 出力済みの記録を書く（記録は消費より先）。`via` が `"claim"` で、計画に `turn` がある時だけ、`output-written/<marker_id>.json` を 1 度だけ作る（4.6。temp を書いて fsync し、`link` で置き、置き場を fsync する。`turn.json` は読まず書かない）。中身は計画の `turn` の身元・`turn_at`（計画の `turn.at`）・`output_written_at`（この時の `now`） | 結果は `written`／`exists`（同じ marker_id の記録がすでにある。上書きせず先の記録を残す）／`failed`（例外。`link` の後の fsync の例外で、記録があるかどうかが分からない時を含む）／`skipped`（`via` が `"marker"`、または計画に `turn` が無い）。`failed` と、claim 経由で計画に `turn` が無い `skipped` は、**段 2 を行わない**（束は `active` のまま = P1） |

`via` が `"marker"`（`clear`／`compact`）の時は、今と同じく記録を書かない（段 1 は `skipped`）。段 2 は行い、順は 出力 → 消費になる。この経路には見張りの確認が無く、消費の後に止まっても『文は既に出力に入っている』（出力は消費より先）。例外は外へ出さず、結果（`record`: written／exists／failed／skipped の理由、`consume`: consumed／lost_race／unknown／skipped）を戻り値で返す。結果は試験が読むために返すだけで、stderr の証拠には出さない（証拠の契約を変えない）。

**なぜ記録を消費より先にするか（2 回目の F1）**: 3 回目の版は 出力 → 消費 → 記録（最後）で、消費が済んだ後・記録の前に process が止まると、束は `consumed`（`getSelectedRestartPack` は `active` だけを返し、store に消費済みの束を読む verb も取り消す verb も無い）で、記録も無く、見張りは HALT で止まるのに、文を出し直す元が code の中に無かった。消費は戻せない一歩なので、その前に『この process が引き継ぎの文を出力に書いた』という事実（記録）を残す。これで**claim 経路の新しい hook からは『消費済みで記録なし』が作られない**（作るのは旧い hook と、他の process が先に消費した場合の `lost_race` だけ。`clear`／`compact` の marker 経路は元から記録を持たず、出力 → 消費の順なので、この状態になりうる。その扱いは 4.7 の marker の行と 4.8 の r5）。記録が書けなかった時（`failed`）に消費しないのは、記録の無いまま束を消すと同じ状態になるため。束が残れば、HALT の後に人が同じ文をもう 1 度出せる（4.7 の R-a）。

なお、消費の更新の応答が失われた時に『更新されなかった』と読まない考え方（1 回目の F1）は変えない。記録が先に済んでいるので、消費の結果を調べる道（非 active の束を読む verb。store に無く、足すと store の口が増える）は要らず、結果に依る判断も作らない。

**確定の線と回復の内部の期限の重なり**: 回復の読み込みの内部の期限は 7000 ms（`CODEX_SESSION_START_INTERNAL_TIMEOUT_MS`。`codex-session-start.ts:45`、Claude は `claude-session-start.ts:67` で同じ値を使う）で、段 0 の `commit_by`（9 秒 − 2 秒 = 7 秒）とちょうど重なる。読み込みが 6.7 秒以上かかって成功すると、段 0 の残りが `ROTATION_COMMIT_WRITE_RESERVE_MS`（300 ms）を割り、何もしない。記録なし・束は `active`・見張りは待ちの後に `unconfirmed` と HALT になる。引き継ぎの文は出力に入っているので、これは 4.8 の r4（文が届いた後の誤った HALT）と同じ形で、安全側の想定内の結果とする。T6(a) がこの場合を固定する。

### 4.4 出力の書き込みの成否の検知と、確定を呼ぶ場所（Claude と Codex の process 層に同じ形）
今の書き込みは成否を返さない（この節の行番号は、5 節の『今の code』と同じく base `94f1ca6d` の file の位置。head では動いている）。Claude の `writeAnswer` は 2 つの書き込みを数えるだけで、callback は誤りを受けない（`claude-session-start.ts:537-547`）。Codex の `writeCliResult` は 2 つの書き込みの後に `process.exit(0)` を直接呼び、注入できる process 層も無い（`codex-session-start.ts:1031-1036`）。

- 新しい共有の小さな module（名前は下書き）に次の 2 つを置く（S3: 「出力が書けた時だけ確定する」という判断は 1 か所）。(a) evidence（stderr）と output（stdout）を書き、output の成否を返す関数。(b) 4.3 の確定を呼ぶ関数。両方の process 層が同じ関数を呼ぶ。
- **成否の基準**: output（stdout）の callback が誤りなしで返り、かつ stdout の `error` event が出ていないこと。evidence（stderr）の失敗は基準に入れない。`error` event は callback の外で出る場合があるので、書く前に一度だけ聞く listener を付ける。**この基準が示すのは『OS の pipe が bytes を受け取った』ことだけで、host が受け取ったことではない**（host は hook が期限の前に終わった時にその出力を使い、期限に達した hook は取り消して出力を捨てる。4.8）。
- **`error` の listener の寿命（3 回目の返却の F2）**: Node の Writable は、書き込みの失敗で write の callback を先に呼び、`error` event をそのあとで出すことがある。書く 1 回ごとの listener を callback の中で外すと、stderr だけが失敗した時に `error` が聞き手なしで出て、未処理の `error` として process が止まる（確定の前）。だから `writeLine` は、(a) stream ごとに『`error` を致命にしない』listener を 1 つだけ付けて残し（`WeakSet` で 1 stream に 1 回）、(b) 書く 1 回ごとの `once("error", finish)` はこれまでどおり callback で外す。成否の基準（stdout の callback が誤りなし、かつ stdout の `error` が出ていない）は変わらず、stderr の失敗は基準に入れない。callback は 1 回だけ呼ぶ。試験（T3(b)）は、手作りの EventEmitter でなく実際の `node:stream` の Writable で、callback→`error` の順と、listener の数が 2 回書いても 1 のままであることを確かめ、E2E は実際の pipe を閉じた子 process で、stdout の失敗は『出力なし・記録なし・消費なし』、stderr だけの失敗は『出力あり・記録あり・消費あり・終了 0』を確かめる。
- Claude: `io.write_output`・`io.write_evidence` の callback を、誤りを受ける型にする（IO は注入できるので T3 を書ける）。確定は `await writeAnswer(...)` の後、`ignoredNames` の分岐と `io.exit()` の前に入れる。診断（`finishAfterAnswer`）は確定の後に流す（`remaining_ms` は確定の後の時計で数えるので、確定の分だけ縮む。T11）。診断は `ignoredNames` がある時だけ起き（`claude-session-start.ts:574-578`）、残りが `HOOK_DIAGNOSTIC_MIN_REMAINING_MS`（2000 ms）以上ある時に始まり、診断が終わるか `min(残り, HOOK_DIAGNOSTIC_MAX_WAIT_MS)`（最大 200 ms）で `exit` する（`hook-input-diagnostics.ts:252-275`、定数 `:17・:19`）。**この待ちは確定（記録と消費）の後で、確定の線（`commit_by`）の外にあり、記録・消費の結果に影響しない。** 4.3・4.5 の『記録の後に待つものが無い』は確定の中の話で、この診断の待ち（最大 200 ms）を除く（2 回目の監査の O2）。
- Codex: `main` の終わりを、Claude と同じ形の IO（`write_evidence`・`write_output`・`exit` に加えて、単調増加の `clock`）を受ける小さな関数に切り出す（挙動は変えない）。経過は `main` の最初に読んだ `clock` から数える（Codex の `main` には今は時計が無い）。確定は書き込みの後・`process.exit(0)` の前に入れる。入力が壊れている早い return（`codex-session-start.ts:1048` 以降の catch 側）は、同じ関数で degraded を書くが、確定の計画が付かないので確定しない。最後の `main().catch`（1094-1098 行、`process.exit(0)`）は切り出しの外で、確定を呼ばない（そこへ来るのは例外で、文が出力に入っていない）。**出力の後の挿入点は Claude と Codex で別々に作る**（共有なのは `prepareRotationRecovery` まで）。`codex-session-start.ts` は 1099 行で 800 行を超えるので、足すのは `main` の数行にとどめる（触る時に直す）。
- hook の期限（9 秒）の定数は Claude と Codex に 1 つずつある（`claude-session-start.ts:68`・`codex-session-start.ts:46`。今ある 2 か所の重複）。この PR は新しい literal を足さず、各 process 層が自分の定数を 4.3 の `hook_timeout_ms` に渡す。

### 4.5 確定の継続を止める線（1 回目の F1 への答え）

確定の中で『待つ可能性のある境目』は 5 つ。**線の引き方は 1 つ: 主の流れ（出力の後の確定を呼んだ側）だけが出力済みの記録に触れ、それ以外の続きは何も書かない。** 主の流れは、段 2 を諦めた時に `abandoned` の旗を立て、以後は待たない。

| 境目 | 起きうること | 取り方 |
|---|---|---|
| 記録の書き込み（段 1） | 同期の fs の呼び出し（temp を書く・fsync・`link`・fsync。待つ物は無い。4.6） | 主の流れが、消費より先に行う。同期の呼び出しの途中は timer で止められない（残る窓は 4.6・4.8） |
| store を開く（`createStore`。段 2） | 予算の後に開き終わる | 予算で競わせる。予算が切れたら `abandoned` を立てる。後から開き終わった続きは、`abandoned` を見て**消費を発行せず**、store を閉じるだけ（閉じるのを待たない） |
| 消費の発行（段 2） | 送った後は、応答が来るまで結果が分からない | 応答が来ない・誤り・予算切れは `unknown`。**再送しない・『更新されなかった』と読まない**。結果を使う判断が無い（4.3） |
| 消費の応答 | 予算の後に応答が来る | 続きは結果を捨てるだけで、記録にも store にも何も書かない |
| store を閉じる | `pool.end()` は戻らないことがある（`stores/pg-store.ts:1318`） | **閉じるのを待たない**（正常でも予算切れでも同じ）。消費は 1 回の更新か書き出しで済んでいて、閉じる事に依らない。process は消費の後に `exit` で終わる |

予算は 2 段: 段 0 の `commit_by`（process の開始から 7 秒）が全体の線、段 2 の予算 `min(ROTATION_COMMIT_BUDGET_MS, commit_by − 経過)` が消費の線。**値の置き場は 2 つ**（2 回目の監査の O1: 前の版の書き方が揺れていた）: 確定の値 `ROTATION_COMMIT_BUDGET_MS`（下書き 1500）・`ROTATION_COMMIT_EXIT_MARGIN_MS`（下書き 2000）・`ROTATION_COMMIT_WRITE_RESERVE_MS`（下書き 300。段 1 の同期の書き込みのための残し）は `constants.ts` の 1 か所、出力済みの記録の schema 名 `ROTATION_OUTPUT_WRITTEN_SCHEMA` は `session-rotation-files.ts` の既存の 3 つの schema 定数の隣。段 0 が『残り ≥ 300』を要り、段 2 の予算は `commit_by` を超えないので、確定は `commit_by` の手前で終わる（超えるのは同期の fs の ms 級の分だけ）。

確認の待ち（60 秒、2 秒ごとに見る）との関係: 出力済みの記録は、出力の直後（段 0 の残りが足りれば、同期の書き込み 1 回の後）に付く。記録は書いたら書き換えられず、`turn` が `busy`／`idle` に変わっても残るので、見張りは待ちの間のどの確認でも読める（`turn.state === "started"` の瞬間を捉える必要が無い）。2 回目の版は印を `turn` の `rotation_marker_id` に置いたので、確認の組（`started` かつ印）が見える時間が『印を書いてから最初の Stop／UserPromptSubmit が書くまで』に縮み、見張りの間隔（2 秒）より短ければ配達に成功しても HALT になりうる、という見直し役の指摘（OPEN-2）を受けた。3 回目の版からこの依存は無い（4.6・4.8）。

### 4.6 出力済みの記録（1 回目の F2 と OPEN-2 への答え。arc の判断で `turn.json` の外に出した。4 回目の版で名前と意味を『観測した事実』に改めた）

2 回目の版は、印を `turn.json` の `rotation_marker_id` に書き、`turn` の全書き手を `turn.lock` で排他にした。しかし 1 回目の F2（読んでから置き換えるまでの間に別の書き手が入る）も、見直し役が見つけた OPEN-2（Stop／UserPromptSubmit の書き手が `busy`／`idle` で上書きすると確認の組が消える）も、根は同じ: **事実という消えない物を、書き手の多い一時の状態の file に置いた**こと。3 回目の版から、事実は別の file に置く。

- **置き場**: 席の置き場の `output-written/<marker_id>.json`（`claims/<marker_id>.json` と同じ型。`marker_id` は marker の中身の SHA-256 で、1 回の切り直しごとに別）。`marker_id` の確かめ（`^[0-9a-f]{64}$`）は `readClaim` が持つもの（`session-rotation-files.ts:231`）を共有の小さな関数にして 2 か所から呼ぶ（S3: 新しい正規表現を書かない）。`turn.json` とは別の file で、Stop／UserPromptSubmit／`prepareRotationRecovery` の書き手は触らない。
- **記録の意味（観測した事実だけ）**: この記録が言うのは『hook が出力（stdout）を書き終え、書き込みの callback が誤りなしで返った』ことだけで、host が受け取ったこと・席が文を読んだことは言わない（成功の宣言を記録しない。S5）。見張りの『確認』は、この記録と、新しい会話についての観測（session・時刻・身元・pane の process）の組から読む。記録の名前・schema・欄に `delivered`／`received` の語を使わない（T15）。
- **中身**（schema 名は新しい名前 `kusabi-rotation-output-written/v1`。既存の `kusabi-rotation-marker/v1`・`kusabi-rotation-turn/v1`・`kusabi-rotation-hook-state/v1` と同じ並びで、定数 `ROTATION_OUTPUT_WRITTEN_SCHEMA` は `session-rotation-files.ts:23-25` の 3 つの隣に置く）: `schema_version`、`marker_id`、計画の `turn` の身元の欄（`agent_id`・`project`・`host`・`session_id`・`source`、`HostIdentity` の欄 = `pane_id`・`tmux_socket`・`host_pid`・`host_started_at`。どれも null でありうる。`session-rotation-files.ts:27-32`）、`turn_at`（計画の `turn.at`）、`output_written_at`（確定の時の `now`）。秘密の値・記憶の中身・引き継ぎの文は持たない。
- **書き方（書いたら書き換えない）**: 書く関数は新しく足す（下書きの名前 `writeJsonOnce`、記録の組み立ては `writeOutputWritten`）。`output-written/` の置き場は `mkdirSync(recursive, mode 0o700)`、file は mode 0o600 で、`claims/` と同じ（`session-rotation-files.ts:188-191` の `writeJsonAtomic` と同じ作り方）。temp（`<path>.<pid>.<n>.tmp`）を書いて fsync → `linkSync(temp, path)`（すでにあれば `EEXIST` で、上書きしない）→ temp を消す → 置き場を fsync。最終の path は完成した内容でだけ現れるので、読み手は途中の内容を見ない。一度現れた記録は誰も書き換えず・消さない。同じ marker_id の 2 度目の書き込みは `exists` で、先の記録が残る。

**読み取り専用の読み手（4 回目の返却の F1。要件 FR11.7）。** 3 回目の版の `handoff-source` は `createStore()` で store を開き `close()` で閉じていた。store を開く・閉じるは書く準備と書く操作を含む: SQLite は `initialize`・`close` が file 全体を書き出す（`db.export` → `writeFileSync`）ので、読んだ後に別の process の通常の保存が入ると閉じる時に巻き戻す（失われた更新）。PostgreSQL は `initialize` が表の作成（migration）を流すので、読み取り専用の接続や SELECT だけの role では、読む前に失敗する（`cannot execute CREATE TABLE in a read-only transaction`）。JSON は `initialize` が古い形の行に `task_id`・`updated_at` を足して書き戻す。引数が足りない時も、確かめの前に store（SQLite の既定の file）を作っていた。直しは、verb の枝と引数の確かめを `createStore()` の前に置き、store を通さない読み手（`src/stores/read-only-task-states.ts`）で読む形:

- S5: 記録を、宣言でなく**出力を書き終えた後の観測した事実**（output の書き込みの成功）に結び、記録と台帳の名前・欄は観測した事実だけを言う（4.6）。成否が分からない時は記録を書かず、消費もしない（観測できずを成功にしない）。**見張りは、受領を観測していない時に成功と書かない**（O4: 終端の値は `output_written_receipt_unobserved`）。結ぶ事実は『OS の pipe が受け取った』までで、host の受領ではない（4.8）。見張りは記録の中身（session・時刻・身元）を観測した process の状態（pane・process の子孫）と突き合わせて読み、記録の存在だけで根拠とは読まない。更新の応答が失われた時は『更新されなかった』と読まず `unknown` とし、その結果に依る判断を作らない。
- S5（4 回目の返却の F1）: 『読むだけ』を宣言でなく観測で示す。実際の command を JSON・SQLite・PostgreSQL で走らせ、前後で DB の file の bytes と更新時刻（SQLite）、store の file 全部の SHA-256（JSON）、行と列（PostgreSQL）が同じことを確かめる（T17(i)(k)、T9(f)）。読めない物（壊れた JSON、無い store、DB でない file、表が無い DB、届かない PostgreSQL）は `unreadable` で、『無い』（`absent`）と読み替えない。
- S6: code だけの変更（`output-written/` は席の置き場の新しい file で、DB の schema の変更ではない。台帳と claim は rotation の置き場の file で、新しい値を足すが欄は足さない）。新しい hook（記録が先・消費が後）と旧い hook（消費が先・印が先）は同じ DB で動く。見張り（読み手）は出力済みの記録も旧い形も読み、どちらも新しい終端の値で終わる。**入れ替えの順は『見張り → hook』**: 旧い見張りに新しい hook が当たると、見張りが記録を読めず HALT（`unconfirmed`）になる。**新しい hook はその時も出力の後に記録と消費を行うので、引き継ぎの文は席に出ている。起きるのは『文は届いているのに HALT』という誤った HALT で、運用者は HALT を消せばよい**（4.7 の『同居』）。この順は配備の段（17.9）の手順に書く（見張りの常駐と hook の settings が同じ release で同時に入れ替わるかは読んでいない）。戻す順は逆（hook を戻してから見張りを戻す）。code を戻せば足り、残った `output-written/` は無害な作業 file。戻した旧い見張りは、新しい `state` の claim を `unreadable`（閉じる側）、新しい `kind` の台帳の行を数えない（4.6・4.8 の r6）。`consumeSelectedRestartPack` は 3 つの store のどれも `status = 'active'` を条件にする（`stores/pg-store.ts:1071-1085`・`stores/sqlite-store.ts:1480-1496`・`stores/json-store.ts:693-699`）。**PostgreSQL は 1 文の条件つき UPDATE なので、複数の process が競っても 1 度だけ効く。SQLite（sql.js）と JSON の store は、1 つの process の中でだけ 1 度だけ効く**（sql.js は process ごとにメモリ上の DB を持ち、`persist()` で全体を書き出す。JSON の store は読んでから書く）。複数の process が同時に消費する時の原子性は無いが、今の store の性質で、この席の本番は PostgreSQL なので、この直しの範囲では直さない。
- S7: 外への効果は『出力済みの記録』と『束の消費』で、順は記録 → 消費。記録は `link` が `EEXIST` で失敗するので二重に書いても 1 つで、内容は先の記録のまま。消費は条件つきの更新で、再送しても効果は 1 回（再送はしない）。
- S8: 確定の失敗を握りつぶさない。失敗は『記録が無く、`claim` が `unconfirmed`・席に HALT』として見える（7 節の 2）。記録の書き込みの失敗は消費をしない形で表に出る（束が残り、R-a で戻せる）。
