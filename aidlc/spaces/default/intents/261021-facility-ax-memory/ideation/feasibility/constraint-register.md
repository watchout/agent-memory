# 制約の一覧

入力: 意図の文書（`ideation/intent-capture/intent-statement.md`）、市場調査の 3 つの文書（`ideation/market-research/competitive-analysis.md`・`market-trends.md`・`build-vs-buy.md`）、この段階の質問 Q1〜Q8 の答え。

## 技術の制約

| ID | 制約 | 出典 | 影響 |
|----|------|------|------|
| C-01 | 今の Kusabi と同じ TypeScript・Node.js・PostgreSQL で作り、前提を変えない | 質問 Q2 | 新しい技術を足さない |
| C-02 | 自社の DB は共通基盤の DB と同じ所に置く | 質問 Q3 | 共通基盤の DB に Kusabi の置き場が要る（C-07） |
| C-03 | 席が誰かは、共通基盤のエージェントの管理で決める。Kusabi は自前の席の一覧を持たない | 質問 Q1（iyasaka-arc#49 6290511960） | 席の見分けを共通基盤に合わせる |
| C-04 | AUN との連動は今回は考えない | 質問 Q1 | 席の間の連絡は範囲の外 |
| C-05 | Claude Code・Codex の組込みの記憶は比べる相手にとどめ、読み込みも書き出しもしない | 質問 Q1、市場調査の Q7 | 席の記憶の正は Kusabi に置く |
| C-06 | 外の記憶の製品は使わない。公開の仕組みは考え方の参考にとどめる | 作るか借りるかの文書（市場調査の Q4） | 自前で作る |

## 組織・進め方の制約

| ID | 制約 | 出典 | 影響 |
|----|------|------|------|
| C-07 | 共通基盤の DB に Kusabi の置き場を入れること、今の記録を移すことは、保護面として Owner の決定が要る | 質問 Q3・Q8 | その時点で Owner の決定を待つ |
| C-08 | 今の記録を移す時は、今の記憶の持ち主（agent_id・project）と共通基盤の席の対応表を通し、表は Owner が承認する。対応の無い記録は推測でつながない | 質問 Q8 | 対応の無い記録は残るが、席にはつながらない |
| C-09 | 今の記録は席ごとに置き場所が違う（SQLite のファイルと PostgreSQL）ので、設計の段で棚卸ししてから移す | 質問 Q8（共通基盤 0.2 の段階導入の決まり） | 設計の段に棚卸しの作業が入る |
| C-10 | Kusabi の新しい実装は停止中（T102）。停止の間は設計の段階まで進め、実装は停止が解けてから | 質問 Q6（iyasaka-arc#49 6329622282） | 実装の開始は停止の解除を待つ |
| C-11 | 新しい費用・有料サービスは Owner の決定なしに使わない。顧客役の DB の試験の環境も、まず自社の機械で用意する | 質問 Q7・Q4 | 試験の環境は自社の機械の範囲 |
| C-12 | 成功の指標は自社が管理できる範囲のものにする | team.md の Mandated（Owner の指示 2026-10-22） | 意図の文書の成功の測り方（試験と一覧）はこれに合う |

## 規制・決まりの制約

| ID | 制約 | 出典 | 影響 |
|----|------|------|------|
| C-13 | 記録は自社か顧客の DB の中で完結させる | 質問 Q5（iyasaka-arc#49 6327956142） | 外のサービスや外の LLM に記憶を出さない |
| C-14 | 個人情報保護法（顧客の仕事の記憶に個人データが入る場合） | 質問 Q5、流れの文書 | 顧客の仕事の記憶を置く段で確認が要る |
| C-15 | 顧客企業ごとの社内の決まり（データの置き場所・持ち出し） | 質問 Q5 | 顧客ごとに置き場所を選べる形で守る |
| C-16 | Shirube 開発規格（参照される行は消さない、DB の作りの変更は戻せる形にする、など） | 質問 Q5 | 元の記録は消さずに残す（C-08 と合う） |
