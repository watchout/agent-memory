# リスク・前提・問題・依存の一覧

入力: 意図の文書（`ideation/intent-capture/intent-statement.md`）、市場調査の 3 つの文書（`ideation/market-research/competitive-analysis.md`・`market-trends.md`・`build-vs-buy.md`）、この段階の質問 Q1〜Q8 の答え、実現性の見立て（`feasibility-assessment.md`）、制約の一覧（`constraint-register.md`）。

起こりやすさと影響の目安: 高・中・低（見込み）。

## リスク（Risks）

| ID | リスク | 起こりやすさ | 影響 | 手当て |
|----|--------|------------|------|--------|
| R-01 | 種類の違う席の間の引き継ぎ（成功の条件 B）は今の版に無く、新しく作る量がいちばん多い。「同じ仕事」を何で見分けるかが決まらないと、試験の場面も決まらない | 中 | 高 | 設計の最初に「同じ仕事」の見分け方を決める |
| R-02 | 停止（T102）が長引き、設計だけが進んで実装が始められない | 中 | 中 | 停止の間は設計の段階まで進める（Q6）。設計は停止の解除後にすぐ使える形で残す |
| R-03 | 今の記録を移す時、対応表で席に結べない記録が出る | 高 | 中 | 推測でつながず「つながっていない記録」として残す（Q8）。成功の条件 C の母数の決め方を設計で決める |
| R-04 | 席ごとに置き場所が違い（SQLite のファイルと PostgreSQL）、棚卸しで想定外の記録や置き場所が見つかる | 中 | 中 | 設計の段で棚卸しを先に行う（Q8） |
| R-05 | 共通基盤の DB は、席ごとの隔離が弱い形を受け入れている。読み書きできる者の一覧（成功の条件 D）が、実際の読み書きを正しく表さない | 中 | 中 | 一覧が何を根拠にするか（登録か、実際の権限か）を設計で決める |
| R-06 | 顧客の仕事の記憶に個人データが入り、個人情報保護法の確認が要る場面が出る | 低（最初の版は社内） | 高（顧客に出す段） | 顧客の仕事の記憶を置く段で法務の確認をする |
| R-07 | 土台にする今の Kusabi の不具合（会話の保存と取り直し、agent-memory#330）が、最初の版に持ち越される | 中 | 中 | 最初の版の範囲に含めるかを範囲の段階で決める |

## 前提（Assumptions）

| ID | 前提 | 確かめ方 |
|----|------|---------|
| A-01 | Claude Code と Codex の席は、どちらも MCP の口から Kusabi を呼べる（Codex の一次資料は今回確かめていない） | 設計の段で一次資料を確かめる |
| A-02 | 共通基盤 0.2 の設計（1 つの PostgreSQL の DB に製品ごとの置き場を置く）に、Kusabi の置き場を足せる（Q3 の答えの根拠） | 設計の段で onza の `docs/common/0.2` を読む |
| A-03 | 顧客役の DB は自社の機械で用意でき、新しい費用がかからない（Q4・Q7） | 試験の環境を作る段で確かめる |
| A-04 | 担当交代と再起動の場面を設計で決めれば、成功の条件の試験は自社で回せる | 試験の場面を決める段で確かめる |
