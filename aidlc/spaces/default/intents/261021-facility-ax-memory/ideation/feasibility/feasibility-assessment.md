# 実現性の見立て — 席の記憶を自社か顧客の DB に保ち、どの席も続きから再開できる

入力: 意図の文書（`ideation/intent-capture/intent-statement.md`）、市場調査の比較の文書（`ideation/market-research/competitive-analysis.md`）、流れの文書（`ideation/market-research/market-trends.md`）、作るか借りるかの文書（`ideation/market-research/build-vs-buy.md`）、この段階の質問 Q1〜Q8 の答え。

## 結論

- **条件付きで作れる。** 意図の文書の成功の条件 4 つ（下の A〜D）は、どれも今の Kusabi と共通基盤の上で作れる見込みがある。ただし見込みであり、作る量は見積もっていない。
- 作り始められるのは設計の段階まで。実装は、Kusabi の新しい実装の停止（T102）が解けてから（質問 Q6）。
- 先に越える必要のある関門が 3 つある: (1) 共通基盤の DB に Kusabi の置き場を入れる Owner の決定（Q3）、(2) 今の記録を移す時の対応表の Owner の承認（Q8）、(3) 停止の解除（Q6）。
- いちばん不確かなのは、種類の違う席の間での引き継ぎ（条件 B）。今の版には無く、新しく作る量がいちばん多い。

## 条件ごとの見立て

| 条件（意図の文書の成功の条件） | 今あるもの | 足りないもの | 見立て |
|------|-----------|-------------|--------|
| A 自社か顧客の DB に置ける | 今の Kusabi は自社の DB に記録を置いている（比較の文書） | 自社の DB を共通基盤の DB に置く（Q3）。顧客の DB に置く形は、自社の機械に顧客役の DB を用意して試す（Q4・Q7） | 作れる。共通基盤の DB へ置き場を入れる Owner の決定が要る |
| B 種類の違う AI の席から同じ記憶を使える | 今の Kusabi は MCP で呼べるが、「同じエージェント／プロジェクトの範囲」の記憶で、エージェントをまたぐ連携は主張していない（比較の文書） | 席が誰かを共通基盤のエージェントの管理で決め（Q1）、「同じ仕事」の記憶を別の席が引き継げるようにする | 作れる見込み。ただし最も不確か。「同じ仕事」を何で見分けるかを設計で先に決める必要がある |
| C 担当交代と再起動の後に、決定・作業の状態・学びを 100% 取り出せる | 回復の道具（recover_context・restart_pack）がある（比較の文書） | 起動の時に自動でつながる所、回復の質の測定、試す場面の取り決め。会話の保存と取り直しの不具合（agent-memory#330）が開いたまま | 作れる。試験の場面を設計で決めれば、自社で測れる |
| D 顧客ごとに、置き場所の DB と読み書きできる者の一覧を出せる | 確かめていない（比較の文書） | 席の登録（共通基盤）と DB の読み書きの権限から一覧を作る | 作れる見込み。ただし共通基盤の DB は席ごとの隔離が弱い形を受け入れており（iyasaka-arc#49 6290511960）、一覧が実際の読み書きを正しく表すかは確かめる必要がある |

## 今の記録の移し（質問 Q8）

- 今の Kusabi の記録は、共通基盤の DB へ移し、元は消さずに残す。
- 移す時は、今の記憶の持ち主（agent_id・project）と共通基盤の席の対応表（Owner が承認）を通し、対応の無い記録は推測でつながない。
- 今の記録は席ごとに置き場所が違う（SQLite のファイルと PostgreSQL）ので、設計の段で棚卸ししてから移す。
- 見立て: 作れる。ただし棚卸しの結果で量が変わる。対応の無い記録は「つながっていない記録」として残るため、成功の条件 C の 100% は、対応表で結べた記録を母数にする必要があるかを設計で決める。（私の読み。母数の決め方は Owner の判断）

## 技術の前提（変えない）

- 今の Kusabi と同じ TypeScript・Node.js・PostgreSQL で作る（Q2）。新しい技術を足さないので、技術の選び直しの不確かさは小さい。
- 外の記憶の製品は使わない（作るか借りるかの文書）。新しい費用・有料サービスは Owner の決定なしに使わない（Q7）。

## 早めに出しておく懸念

- 条件 B（種類の違う席の間の引き継ぎ）が決まらないと、成功の条件の試験の場面も決まらない。設計の最初に扱うべき。
- 停止（T102）の解除がいつになるかで、最初の版が使い始められる時が決まる。この段階では動かせない。
- 個人情報保護法の確認（流れの文書）は、社内の開発の席で使い始める最初の版には影響が小さい見込み。顧客の仕事の記憶を置く段で効く。（見込み）

## 確かめていないこと

- 作る量の見積もり。
- Codex の席が MCP で Kusabi を呼べることの一次資料（今回の調査では確かめていない）。
- 共通基盤 0.2 の設計に Kusabi の置き場を足せること（Q3 の答えが根拠に挙げた onza の `docs/common/0.2` は、この段階では読んでいない）。
