# 使い手（ペルソナ）

要件（`inception/requirements-analysis/requirements.md`）と、話の立て方の Q1 = A から。最初の版に人が見る画面は無く、P-A・P-B は道具の応答と起動の時の回復で、P-C は道具の応答と試験の結果で、P-D は owner が見せる一覧で受け取る。

## P-A 記憶を書く席

- **役割**: 実装・設計・監査などの仕事をする自社の席（AI）。種類は Claude Code・Codex・Gemini。共通基盤のエージェントの管理に登録され、1 つの顧客に所属する
- **目的**:
  - 決めたこと・作業の途中の状態・学んだことを残し、再起動や圧縮の後に自分で続きを始める
  - 種類が替わっても（Codex から Claude Code へなど）同じ記憶で仕事を続ける
- **困りごと**:
  - 会話の区切りで記憶を失い、同じ説明や判断をやり直している（意図の文書の問題）
  - 置き場所の DB に届かない時に、記憶が残ったのかどうかが分からない
- **使い方**: 仕事の間ずっと（道具を呼ぶ・起動の時に回復を受け取る）
- **道具への慣れ**: 高い（MCP の道具を直接呼ぶ）

## P-B 仕事を引き継ぐ席

- **役割**: 別の役割で、前の担当が進めた仕事の続きを始める自社の席（AI）。指示には仕事の GitHub の issue か PR の URL が書かれている
- **目的**:
  - 指示の URL だけで、前の担当の決定・作業の状態・学びを読み、人に経緯を聞かずに始める
- **困りごと**:
  - 担当が替わると前の担当の経緯が引き継がれない（意図の文書の問題）
  - 前の担当が引き継ぎを書く前に止まると、何も残らない
- **使い方**: 担当が替わった時（仕事の始めに 1 回）
- **道具への慣れ**: 高い

## P-C owner

- **役割**: 席に仕事を任せ、置き場所・今の記録の移し・対応表・保護面を決める人。試験の結果で完了を判定する
- **目的**:
  - 席が担当交代と再起動の後に続きから始められることを、試験の数で確かめる
  - 記憶が自社か顧客の DB の中で完結し、外へ出ていないことを確かめる
  - 今の記録を失わずに新しい置き場所へ移す
- **困りごと**:
  - 席が記憶を失うたびに、経緯を説明し直している
  - 今の記録が席ごとに別々の置き場所（SQLite のファイルと PostgreSQL）にあり、全体が見えない
- **使い方**: 決定の時・試験の結果を見る時・移しの時
- **道具への慣れ**: 中くらい（道具の応答と試験の結果を読む。席を通して道具を使う）

## P-D 顧客企業の情報システムの担当

- **役割**: 顧客企業で、データの置き場所と持ち出しの決まりを受け持つ人。最初の版では直接の使い手ではなく、owner が一覧を見せる相手
- **目的**:
  - 自社の仕事の記録がどの DB にあり、誰が読み書きできるかを確かめる
  - 自社の記録が別の顧客の席から読めないことを確かめる
- **困りごと**:
  - AI の記憶が外のサービスに置かれ、自社の管理下に置けない（意図の文書の問題）
- **使い方**: 導入を決める時・監査の時（owner から一覧を受け取る）
- **道具への慣れ**: 低い〜中くらい（道具は使わない）

## 使い手の関係と優先度

| 優先 | 使い手 | 理由 |
|------|--------|------|
| 1 | P-A 記憶を書く席 | 記憶の持ち主は席（D-01）。最初に得をする |
| 2 | P-B 仕事を引き継ぐ席 | 意図の文書の問題の中心（担当交代）。試験の場面 S4・S5 |
| 3 | P-C owner | 席に仕事を任せ、完了を判定し、保護面を決める |
| 4 | P-D 顧客企業の情報システムの担当 | 成功の条件の 2 つ目（顧客に証明）の受け手。最初の版では owner を通して受け取る |

- P-A と P-B は同じ席が場面によって替わることがある（ある仕事では書く席、別の仕事では引き継ぐ席）。
- P-D が受け取る一覧は P-C が出して見せる。
