# 利用者の話 — 話の立て方の案と質問

要件（`inception/requirements-analysis/requirements.md`）から利用者の話（「誰が・何をしたい・それで何が得られる」と受入の条件）を作ります。立て方の案を示し、owner の判断が要る所だけを聞きます。

## 立て方の案（聞き直さない所）

- 話の形: 「〔使い手〕として、〔したいこと〕をしたい。〔得られること〕のために」。受入の条件は Given/When/Then（inception の決まり）
- 話の良し悪しの物差し: INVEST（独立・相談できる・価値がある・見積れる・小さい・試せる）
- 優先度: MoSCoW（Must・Should・Could・Won't）。最初の版の境目は後の計画の段で決める
- 試験の場面 S1〜S5（要件 FR4）は、その場面を受け持つ話の受入の条件として書き、場面ごとに 1 つ以上の受入の条件を置く
- 人が見る画面は無いので、受入の条件は道具の応答・起動の時の回復・DB の中身で確かめる形にする

## Q1. 使い手（ペルソナ）を誰にするか

案:
- P-A 記憶を書く席（実装などの仕事をする AI の席。種類は Claude Code・Codex・Gemini）
- P-B 仕事を引き継ぐ席（別の役割で、前の担当の仕事の続きを始める席）
- P-C owner（席に仕事を任せ、置き場所・移し・対応表などを決める人）
- P-D 顧客企業の情報システムの担当（自社の記録がどこにあり誰が見られるかを確かめたい人。最初の版では owner が一覧を見せる相手）

A. P-A〜P-D の 4 つ
B. P-A〜P-C の 3 つ（顧客は最初の版では直接の使い手にしない。一覧の話は owner の話として書く）
C. Not yet defined（まだ決まっていない）
X. Other (please specify)

（勧め: A。成功の条件の 2 つ目は「記憶がどこにあり誰が見られるかを顧客に証明できる」で、得をするのは顧客。顧客の担当の合意は顧客の DB に置く形を出す段で取ると決めてある（D-35）が、話の受け手としては今から置いておくと、一覧の受入の条件を顧客の目で書ける）

[Answer]: A（arc の下書き。成功の条件の 2 つ目「記憶がどこにあり誰が見られるかを顧客に証明できる」= intent-statement の表で、得をするのは顧客。P-D の話は、一覧の受入の条件を顧客の目で書くために置く。最初の版で顧客が直接使う物は作らず、一覧は Owner が見せる（顧客の担当の合意は顧客の DB に置く形を出す段で取る = D-35）。指標は自社が出せる一覧で確かめる形にする = iyasaka-arc#49 6329643565）

## Q3. 会話の取り込み（P8、要件 FR8）の優先度

会話の取り込みは最初の版に入れると決めてありますが、完了の判定（2 つの条件）には入っていません。完了に含めるかは後の計画の段で決めることになっています。話の優先度をどう置くかを決めます。

A. Must（最初の版で必ず仕上げる）
B. Should（最初の版に入れるが、完了に含めるかは計画の段で決める）
C. Could（余裕があれば入れる）
D. Not yet defined（まだ決まっていない）
X. Other (please specify)

（勧め: B。範囲の段の決定（最初の版に入れる）と、計画の段で完了との関係を決める決まり（範囲の文書の確かめていないこと）の両方に合う）

[Answer]: A（arc の下書き。範囲の段で Owner が「最初の版に入れる」と答え、intent-backlog の 7 行目に Must と記録済み。完了の判定（2 つの条件）に含めるかは、範囲の文書の「確かめていないこと」のとおり計画の段で確かめる。ここで Should に下げると、Owner の答えを変えることになる）
