# 利用者の話の要否の見極め

## 決定

- 行う（Execute）

## 理由

- 使い手が 1 種類ではない。記憶を書く席、別の役割で仕事を引き継ぐ席、席に仕事を任せて決定する owner、記憶の置き場所と見られる者を確かめたい顧客がいて、それぞれ得るものが違う。（要件の意図の分析、FR1〜FR6）
- 決まりが入り組んでいる。仕事の ID での引き継ぎ（FR2）、顧客の間の隔離（NFR2）、置き場所の DB に届かない時に逃げないこと（FR5.3）、移しで推測で結ばないこと（FR7.3）など、「誰が・何を・どうしたら」で書かないと試験の形にしにくい。
- 成功の条件の試験（場面 S1〜S5、FR4）を、利用者の話の受入の条件（Given/When/Then）にそのまま落とせる。試験を先に書く進め方（team-practices.md の Testing Posture）と合う。
- 共通基盤のエージェントの管理・配車の席など、ほかの席の仕事と関わる。

## 考えた要素

| 要素 | 見立て |
|------|--------|
| 種類 | 既存の仕組み（Kusabi 0.3.0）への機能追加。開発の席が使う道具の面もあるが、使い手が複数で、純粋な道具の手直しではない |
| 人の見る画面 | 無い（最初の版は画面を作らない、D-33）。使い手は主に席（AI）で、道具の応答と起動の時の回復で受け取る |
| 複雑さの印 | 引き継ぎ・顧客の隔離・置き場所の選択・移しの決まり、5 つの場面の試験 |

## 話が最も役に立つ所

- 別の役割の席への引き継ぎ（S4）と、仕事の ID での読み出し
- 顧客の間の隔離と、置き場所と読み書きできる者の一覧（顧客に見せる証明）
- 今の記録の移し（対応表・結べない記録・元を消さない）
- 外へ出さないこと（埋め込みを止める・呼出しの記録に記憶の文を書かない）
