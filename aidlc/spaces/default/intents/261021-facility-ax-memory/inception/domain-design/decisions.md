## ADR-001: 顧客の DB は、共通基盤と Kusabi の置き場を持つ、顧客ごとの 1 つの DB にする

### Context

- 置き場所は顧客ごとに、自社（共通基盤の DB）か顧客の DB のどちらか一方を選ぶ（決定 D-04・D-17）。
- 共通基盤の決まりでは、製品は保存と同じ transaction で、共通基盤の確かめの関数を呼ぶ（contract.md §5）。本人の確かめは DB の利用者（`session_user`）から行う（architecture.md §4）。
- 顧客の記録・読み書きできる者の一覧は、顧客の DB の中で完結させる（制約 C-13・C-15、要件 FR5.2・FR6）。

### Decision

顧客の DB は、その顧客のための 1 つの DB にし、共通基盤の置き場（`common`）と Kusabi の置き場（`kusabi`）の両方を持たせる。顧客の仕事をする席は顧客の DB の共通基盤に登録し、身元の確かめと記憶の保存を、同じ DB の同じ transaction で行う。

### Consequences

- 良い面: 共通基盤の決まりをそのまま守れる。顧客の記録・身元・読み書きできる者の一覧が顧客の DB の中で完結する。自社の DB が止まっても顧客の席は書ける。
- 悪い面: 顧客ごとに席の登録が要る。顧客の DB にも共通基盤の配布物（同じ版）を入れる必要がある。
- 中立: 試験の顧客役の DB（自社の機械、D-18）に共通基盤の置き場を入れるのは DB の作りの変更で、owner の決定の後に行う（保護面）。共通基盤を顧客の DB に置く形は、Suite と OmotenasuAI が共に使う台帳の置き方に関わる。

### Alternatives Rejected

- 席の身元は自社の DB の共通基盤で確かめ、記憶だけを顧客の DB に書く: 身元と保存が別の DB になり、共通基盤の決まり（同じ transaction）から外れる。自社の DB が止まると顧客の席が書けない。owner が Q1 で A を選んだ。

## ADR-002: 置き場所は席の起動の設定で渡し、Kusabi は「顧客 → 置き場所」の表を持たない

### Context

- 要件 FR5.1 は、顧客ごとに置き場所を決める設定を求める。FR5.5 は、Kusabi 専用の設定だけを読み、汎用の `DATABASE_URL` を読まないことを求める。
- ADR-001 により、顧客の席は顧客の DB の共通基盤にしか登録されない。

### Decision

置き場所は、席の起動の設定で渡す Kusabi 専用の DB の設定で決める。顧客 Z の仕事をする席には顧客 Z の DB の設定を渡す。Kusabi は「顧客 → 置き場所」の表を持たない。

### Consequences

- 良い面: 設定を間違えて別の DB を渡しても、その DB に登録の無い席は断られる（FR1.2）。間違いが記憶の漏れにならない。自社の DB が止まっても、顧客の席の起動に響かない。
- 悪い面: 顧客ごとの置き場所の全体を 1 か所で見る表が無い。一覧（FR6）は DB ごとに出す。
- 中立: 設定を渡すのは、席を起動する人か配車の席。今 `DATABASE_URL` だけで動いている席の切り替えの手順は、後の設計の段で棚卸しと合わせて決める（要件の未決の問い）。

### Alternatives Rejected

- 自社の共通基盤の DB に「顧客 → 置き場所」の表を持つ: 自社の DB が顧客の置き場所の一覧を持つことになり、自社の DB が止まると顧客の席が起動できない。Q2 で A を選んだ。

## ADR-003: 仕事の ID を正規の形で記録に付け、同じ所属範囲の席に読ませる

### Context

- 別の役割の席への引き継ぎは、仕事の ID（GitHub の issue・PR の URL）で見分け、同じ顧客の席なら読める（要件の Q2 = A、FR2）。仕事の ID が付いていない記録は、書いた席だけが読める（FR2.4）。
- 前の担当が付け忘れると、引き継ぐ席が読めない（要件の前提 AS10）。

### Decision

- 仕事の ID は `owner/repo#番号` の正規の形にそろえて記録に付ける。形の違う URL は同じ仕事にまとめ、形でない文字列は断る。
- 仕事の ID が付いた記録は、同じ所属範囲の席なら誰でも読める。付いていない記録は書いた席だけが読める。所属範囲をまたいで読ませない。
- 席の起動の時に仕事の ID を設定で渡せば、その会話で書く記録に自動で付く。道具の呼出しで別の ID を渡せばそれを優先する。仕事を次々に替える長く動く席（arc・suite-lead など）は、道具を呼ぶたびに ID を渡す。

### Consequences

- 良い面: 新しい担当は指示の URL だけで続きを読める。1 つの仕事のために起動した席は付け忘れが減る。
- 悪い面: 長く動く席では、起動の時の ID がすぐ古くなるので、呼ぶたびに渡す手間が残る。
- 中立: 今の版の境目（席ごとの非公開）は、仕事の ID が無い記録で保たれる。起動の設定を渡す仕組みは AUN と連動させない（制約 C-04）。

### Alternatives Rejected

- 道具を呼ぶたびに必ず渡す（起動の設定を持たない）: 付け忘れが残る。この段階の Q3 で B を選んだ。
- 前の担当が引き継ぎの記録を書き、受け取る席を名指す: 前の担当が書く前に止まると読めない（要件の Q2 で採らなかった）。

## ADR-004: 席の確かめを共通基盤に寄せ、SeatIdentity を独立の部品にする

### Context

- 席が誰かは共通基盤のエージェントの管理で決め、Kusabi は自前の席の一覧を持たない（制約 C-03、FR1.1）。
- 今の版は、`AGENT_MEMORY_AGENT_ID` の環境の値で記憶の持ち主を決める。共通基盤の決まりでは、渡された値を本人の証拠にしない（architecture.md §4）。
- 席の確かめは 6 つの部品（記録・回復・一覧・移し・会話の取り込み・道具）が使う。

### Decision

席の確かめは、接続した DB の利用者から共通基盤の確かめの関数で行う。その受け持ちを SeatIdentity という独立の部品に置き、ほかの部品はこの部品を通して席を確かめる。

### Consequences

- 良い面: 共通基盤の版が上がった時に直す所が 1 つで済む。同じ確かめの決まりが全部品で同じになる（設計・実装の標準 S3）。
- 悪い面: 席ごとに DB の利用者が要る。今の `agent_id` の環境の値で動いている席は、共通基盤への登録と DB の利用者の用意が要る（移しと合わせて設計の段で扱う）。
- 中立: 手元の機械では席ごとの隔離が弱いことは受け入れ済み（iyasaka-arc#49 6290511960）。一覧（FR6）がその食い違いを出す。

### Alternatives Rejected

- 席の確かめを MemoryRecords の中に入れる: 回復・一覧・移し・会話の取り込みが記録の部品を通さないと席を確かめられず、記録の部品が共通基盤の版に引っ張られる。後で分けると呼んでいる所を全部直すことになる。
- 今の版のまま `agent_id` の環境の値で続ける: 制約 C-03 と共通基盤の決まりに合わない。

## ADR-005: 埋め込みと AUN の表の読み出しをやめる

### Context

- 今の版は PostgreSQL の時、決定・作業の状態・知識の文を Voyage AI に送って埋め込みを作る。鍵は AUN と共用のファイルからも読む。
- 記憶の中身を外の API に送らない（固い決まり、制約 C-13、NFR1）。最初の版は埋め込みを止め、文字の検索だけにする（要件の Q4 = C）。
- 今の版は、同じ DB に AUN の `agent_messages` 表があれば読む。AUN との連動は範囲の外（制約 C-04）。共通基盤の決まりでは、製品はほかの製品の表を読まない。

### Decision

新しい置き場所の Kusabi は、埋め込みを作らず、Voyage AI を呼ばない。探すのは DB の中の文字の検索だけにする。AUN の表は読まない。

### Consequences

- 良い面: 記憶の中身が外へ出る経路が無くなる。鍵のファイルの有無で振る舞いが変わらない。製品の境目が守られる。
- 悪い面: 似た意味の記録を探す力が下がる。回復の内容に AUN のメッセージが入らなくなる。
- 中立: 自社の中で動く埋め込みは後の版で owner が決める（新しい依存）。今の置き場所の埋め込みの列は移しの対象にしない。

### Alternatives Rejected

- 埋め込みを残し、鍵が無い時だけ止める: 鍵がある席では外へ出る。固い決まりに合わない。
- 自社の機械の中で動く埋め込みに替える: 新しい依存の決定が要り、最初の版の完了の判定に入っていない（要件の Q4 で C を選んだ）。

## ADR-006: 場面の試験は、起動の口と道具の呼出しを再現して数える

### Context

- 完了の判定は、場面 S1〜S5 の試験で取り出せる割合 100%（決定 D-27、要件 FR4）。「取り出せた」の数え方は要件の Q7 = B で決めた。
- 取り出した記録を席の LLM が実際に使うかは、LLM の振る舞いで、自社が管理できる範囲の外（team.md の Mandated）。
- 試験は人の手を入れずに再現でき、同じ準備で同じ結果になること（FR4.6・NFR10）。

### Decision

場面の試験（ScenarioHarness）は、席の起動の口と MCP の道具の呼出しを、本物の席と同じ形で再現して回す。数えるのは、Kusabi が起動の時の回復の内容と道具の応答に記録を入れて返したか。本物の席での確かめは、席の種類ごとに 1 回ずつ別に行い、証拠として残す（数には入れない）。

### Consequences

- 良い面: 数える物が自社の管理の中にある。毎回同じ結果になり、CI や手元で再現できる。
- 悪い面: 本物の席の道具の変化（起動の hook の形の変更など）は、再現の試験だけでは見落とすことがある。本物の席での確かめで補う。
- 中立: 本物の席での確かめのうち Gemini は使い捨ての会話を起こすことになり、それは席の起動なので、その時に owner の決定を取る（決定 D-31）。

### Alternatives Rejected

- 本物の席で回して数える: LLM の振る舞いが数に入り、同じ準備でも結果が揺れうる。
- 再現と本物の両方で 100% を完了の条件にする: 本物の側が揺れると完了の判定が自社の管理の外に出る。この段階の Q4 で A を選んだ。

## ADR-007: 今の記録の移しを独立の部品にし、元の置き場所は読むだけにする

### Context

- 今の記録は席ごとに置き場所が違う（SQLite のファイルと PostgreSQL）。棚卸ししてから、owner が承認した対応表を通して移し、元は消さない。対応の無い記録は推測でつながない（決定 D-22、制約 C-08・C-09、FR7）。
- 共通基盤の DB への移しは保護面で、owner の決定が要る（制約 C-07）。

### Decision

今の記録の棚卸し・移し・戻す手順の試しを LegacyMigration という独立の部品に置く。この部品だけが元の置き場所を読み、元の置き場所には書かない。移した記録は MemoryRecords と ConversationIngest を通して書く。

### Consequences

- 良い面: 元の置き場所に触れる所が 1 つに限られ、元を消さない・変えないことを部品の境目で守れる。移しの記録（対応表の版・流した回・つながっていない記録）が残る。移しが済めば使わなくなる部品で、ほかの部品を汚さない。
- 悪い面: 移しのための記録（SeatMapping・MigrationRun・UnlinkedRecord）を持つ表が増える。
- 中立: 対応表の下書きは棚卸しから作れるが、承認は owner。移しを流すのは owner の決定の後。

### Alternatives Rejected

- 移しを MemoryRecords の中の機能にする: 記録の核が元の置き場所の形（SQLite のファイル・今の表）を知ることになり、移しが済んだ後も古い形のコードが残る。
- 移しをせず、新しい置き場所で記録を一から始める: 決定 D-22（今の記録を移す）に合わない。
