# 作る順の計画（Bolt の並び）

- **Bolt**（ボルト）は、作る段（Construction）を 1 回通して、1 つ以上の作業の単位を「動く物」まで仕上げる一区切り。
- **薄い一本**（walking skeleton）は、本当の機能を入れる前に、部品どうしが端から端までつながって動くことを確かめる最小の版。
- 入力: 作業の単位（`inception/units-generation/unit-of-work.md`）、単位の依存（`inception/units-generation/unit-of-work-dependency.md`）、単位と話の対応（`inception/units-generation/unit-of-work-story-map.md`）、取り決め（`inception/contract-design/contract-summary.md`）、要件（`inception/requirements-analysis/requirements.md`）、利用者の話（`inception/user-stories/stories.md`）、部品の一覧（`inception/domain-design/components.md`）、進め方（`inception/practices-discovery/team-practices.md`）、この段階の Q1〜Q2

## 進め方

- 1 つの Bolt = 1 つの単位。一つずつ順に進める（単位ごとに設計の段とコードを書く段を回し、確かめてから次へ）
- 単位ごとの設計の段（Functional Design・NFR など）は、この AI-DLC の会話（aidlc-kusabi）で進め、arc が問いに下書きし owner が確かめる。コードを書く段からは、停止（T102）が解けて Kusabi の順番（Shirube・AUN → Onza → Tsumama → Kusabi、D-32）が来た時に kusabi の席に渡す（Q1 = A）
- 統合は merge commit。独立の監査（devauditor）の PASS の後に、作者と別の席（suite-lead）が head の一致を確かめて統合する（team.md の Way of Working）
- 成功の条件の場面の試験を、その場面を作る実装より先に書く（team.md の Testing Posture）

## 最初の版の完了の判定

次の 4 つがそろった時に完了とする（D-27 に Q2 = A で 2 つを足した）。

1. 場面 S1〜S5 の試験で、決定・作業の状態・学びを取り出せる割合が 100%（母数は試験の場面で作った記録だけ）
2. 顧客ごとに、記憶の置き場所の DB と、読み書きできる者の一覧を出せる
3. 今の記録を移して、席が新しい置き場所で動く（記憶を失わずに切り替わる）
4. 会話の取り込みが、新しい置き場所で動く

## B1 — U1 u1-seat-memory-skeleton（薄い一本）

- **薄い一本**: はい。確かめる所: 専用の設定 → 置き場所の DB への接続 → 共通基盤での席の確かめ → 決定を書く → 再起動 → 別の種類の席の起動の口で読み戻す
- **済みの条件**:
  - 自社の機械の使い捨ての試験の DB で、試験の中で共通基盤 0.2・0.3 と Kusabi の置き場を作り、試験の席を登録して、終われば消す
  - Codex の席の道具から決定を 1 件書き、Claude Code の席の起動の口で同じ決定が回復の内容に入る
  - 登録の無い席・所属の無い席は理由つきで断られる
  - 置き場所の DB を止めると、書き込みは失敗として返り、手元の SQLite に書かれず、席の起動は止まらない
  - 汎用の `DATABASE_URL` だけの時は表を作らず、設定の名前を挙げて止まる
  - 呼出しの記録に決定の文が無い
  - 今ある試験（`npm test`）が通ったまま
- **確かめたいこと**: 共通基盤 0.2・0.3 の確かめの関数を、Kusabi の保存と同じ transaction で呼べる。種類の違う席の起動の口から、同じ DB の同じ席の記憶が読める
- **見せ方**: owner の前で、試験の DB を作る → Codex の席の形で決定を書く → 再起動 → Claude Code の席の起動の口の出力に決定が出る、を 1 本の試験の命令で流す
- **owner の決定が要る所**: 使い捨ての試験の DB を手元の機械の PostgreSQL に作ること（AUN の結合の試験の分とまとめて伺う）

## B2 — U8 u8-scenario-harness

- **済みの条件**:
  - 場面 S1〜S5 の試験があり、数え方（回復の内容に入っていた記録と、仕事の ID だけで道具を 1 回呼んで返った記録だけ）と母数（試験の場面で作った記録だけ）が試験で確かめられている
  - S3 の最小（決定）が通り、ほかの場面は、まだできていない所の理由つきで失敗する
  - 回せない場面は「観測できず」と出て、成功に数えない
  - 外への通信が 0 件、同じ準備で 2 回流すと同じ結果
- **確かめたいこと**: 完了の判定の数を、自社の機械で人の手を入れずに出せる
- **見せ方**: 試験の命令の結果（場面ごとの数・全体の割合・観測できず・結べなかった古い記録の件数 = not_run）

## B3 — U2 u2-memory-records

- **済みの条件**:
  - 作業の状態・学びが書ける。仕事の ID が正規の形にそろい、形の違う 4 通りの URL が 1 つの仕事にまとまる
  - 同じ所属範囲の別の役割の席が、仕事の ID で前の担当の記録を読める（S4 の記録の部分）。別の所属範囲の席は読めない。仕事の ID の無い記録は書いた席だけ
  - 同じ仕事の作業の状態が席ごとに残る。ほかの席の記録を置き換えられない
  - 文字の検索が通り、埋め込みを作らず、外への通信が無い
- **確かめたいこと**: いちばん不確かな所（仕事の ID での引き継ぎ）が、DB の関数の口（席には関数だけを許す）で守れる
- **見せ方**: 場面の試験で S4 の記録の取り出しが通り、隔離の試験が通る

## B4 — U3 u3-recovery-and-hosts

- **済みの条件**:
  - 起動の時と圧縮の後の回復の内容に、作業・決定・学び・最近の会話が入る（S1・S2・S3）
  - 仕事の ID 1 回で 3 種類がまとめて返る（S4）
  - 記録がデータの枠で出て、入りきらない時は省いた件数が出る
  - 起動の口の期限（7 秒）の中で終わり、間に合わない時は起動を止めない
  - Gemini の起動の口があり、S5 が回せる（使い捨ての Gemini の会話を起こすのは、その時に owner の決定を取る）
  - 回復の設定は自分の物だけ書き換えられる
- **確かめたいこと**: 場面 S1〜S5 がそろい、完了の判定の 1 つ目（100%）を数で示せる
- **見せ方**: 場面の試験の結果で S1〜S5 が通る

## B5 — U4 u4-customer-placement

- **済みの条件**:
  - 共通基盤と Kusabi の置き場を持つ顧客役の DB で、顧客の席の身元の確かめと保存が同じ transaction で通る
  - 顧客の席の記録が顧客役の DB にだけあり、共通基盤の DB と手元のファイルに無い
  - 顧客の DB の資格情報が失敗の文・起動の時の文脈・呼出しの記録に出ない
- **確かめたいこと**: 顧客ごとの 1 つの DB の形（ADR-001）で、記録と身元が顧客の DB の中で完結する
- **見せ方**: 顧客役の DB を相手に、書く・読む・置き場所の外に写しが無いことを確かめる試験
- **owner の決定が要る所**: 顧客役の DB に共通基盤の置き場を入れること（DB の作りの変更）

## B6 — U5 u5-access-report

- **済みの条件**:
  - 置き場所ごとに、実際の DB の権限から作った読み書きできる者の一覧が道具の応答で返る（記憶の中身を返さない）
  - 共通基盤の登録との食い違い（登録に無いのに読める者・登録にあるのに読めない者）が出る
  - 権限を読めない時は「観測できず」
- **確かめたいこと**: 完了の判定の 2 つ目（顧客に見せる一覧）が、実際の境目を表す
- **見せ方**: 試験の環境で権限を足す・外すと、一覧の食い違いに出る

## B7 — U6 u6-conversation-ingest

- **済みの条件**:
  - Claude Code・Codex の会話の記録が、伏せ字の処理をされて、席の所属の置き場所にだけ入る
  - 隠れた推論と開発者向けの指示の本文が入らない。2 回流しても重ならない
  - 最近の会話の読み出しが所属範囲をまたがない
- **確かめたいこと**: 完了の判定の 4 つ目（会話の取り込みが新しい置き場所で動く）
- **見せ方**: 試験の会話の記録を取り込み、置き場所と伏せ字と重ならないことを確かめる試験

## B8 — U7 u7-legacy-migration

- **済みの条件**:
  - 今の記録の棚卸し（置き場所ごと・持ち主ごと・種類ごと）が出る。元は変わらない
  - owner が承認した対応表に従って移り、対応表に無い記録が「つながっていない記録」として数えられる
  - 2 回流しても同じ、途中で止めても流し直せる
  - 切り替えの前に、元の置き場所へ戻す手順が試され、戻した席が切り替えの前と同じ回復の内容を受け取る
  - 試験の結果に、結べなかった古い記録の件数が割合とは別の行で出る
- **確かめたいこと**: 完了の判定の 3 つ目（今の記録を移して席が新しい置き場所で動く）
- **見せ方**: 合成の古い記録（SQLite のファイルと PostgreSQL）を移し、元が変わらないこと・件数・戻す手順を確かめる試験
- **owner の決定が要る所**: 対応表の承認、共通基盤の DB への移し（本番）

## 計画の段から作る段への申し送り

- 本番の共通基盤の DB に Kusabi の置き場を入れること、席の展開（R1 → R2 → R3）は、すべての Bolt の後の展開の段で、owner の決定を受けて行う（制約 C-07、team.md の Deployment）
- PostgreSQL の試験は、最初は手元で回して結果を PR に載せ、置き場所の設計が固まったら CI に入れる（その時に owner の exact-head、team.md の Testing Posture）
- 各区切りで使う確かめの命令は、まだ決めていない。owner の指示で、作る段の最初の区切りで決める（網羅率の確かめ方と、PostgreSQL の試験に使う使い捨ての DB の扱いが、その時までに決まるため）
